1. 이 문서는 무엇을 설명하나요?

이 프로젝트는 HTML 페이지, CSS 스타일, 브라우저 JavaScript, Supabase 서버 함수가 함께 작동하는 웹 프로젝트입니다. 화면에서 버튼을 누르면 JavaScript가 입력을 확인하고, 필요한 경우 Supabase의 RPC 함수를 호출합니다.

아래 내용은 저장소에서 확인되는 코드에 근거합니다. 서버 함수 내부에서 실제로 어떤 SQL을 실행하는지, 비밀번호를 어떤 방식으로 저장하는지처럼 서버 정의가 필요한 사항은 별도로 구분합니다.

HTML CSS JavaScript Supabase RPC

2. 전체 작동 흐름

① 사용자가 화면에서 동작

예: 계정 생성, 로그인, 게임 설정 확인, 관리 기능 실행

↓
② 페이지 JavaScript가 입력을 처리

입력값을 읽고 기본 형식을 확인한 뒤, 필요한 API 함수를 호출합니다.

↓
③ `assets/js/game-api.js`가 요청을 보냄

공통 `rpc()` 함수가 Supabase REST RPC 경로에 POST 요청을 보내고 JSON 응답과 오류를 처리합니다.

↓
④ Supabase 서버 함수가 요청을 처리

요청 이름에 해당하는 서버 함수가 실행됩니다. 실제 데이터 검증, 권한 확인, 데이터 변경의 안전성은 서버 함수의 구현과 데이터베이스 정책에 달려 있습니다.

↓
⑤ 결과를 화면에 반영

성공하면 받은 데이터를 화면이나 브라우저 세션에 반영하고, 실패하면 오류 메시지를 표시합니다.

3. 주요 파일의 역할

index.html

홈 화면의 HTML 구조입니다. 로그인 영역, 로그인 후 화면, 개발자 탭 같은 요소의 위치와 ID를 정의합니다.

assets/css/

색상, 여백, 카드, 버튼, 반응형 배치 등 화면 디자인을 담당합니다. CSS는 화면의 모양을 바꾸지만, 서버 권한을 부여하지는 않습니다.

assets/js/pages/new-home.js

홈 화면의 계정 생성과 로그인 버튼, 로그인 상태에 따른 화면 표시, 게임 설정 조회, 개발자 탭 이동을 처리합니다.

assets/js/game-api.js

Supabase RPC 요청을 보내는 공통 함수와 계정·관리 기능별 호출 함수, 브라우저 세션 저장·조회·삭제 및 입력 형식 확인 함수를 제공합니다.

assets/js/config.js

Supabase 프로젝트 URL과 브라우저에서 사용하는 공개용 키, 학년 및 학급 관련 설정을 정의합니다. 브라우저 코드에 서버 비밀 키를 넣으면 안 됩니다.

developer/index.html

개발자 센터의 기능별 링크를 모아 둔 페이지입니다. 실제 각 기능은 연결된 HTML과 JavaScript 파일에서 구현됩니다.

developer/code-guide.html

이 문서 페이지입니다. 개발자 권한을 확인한 뒤 프로젝트 구조와 주요 메커니즘을 설명합니다.

4. 로그인과 계정 생성 메커니즘

  1. 홈 화면에서 닉네임과 비밀번호를 입력합니다.
  2. new-home.js가 requireNickname()과 requirePassword()로 입력 형식을 검사합니다.
  3. 계정 생성은 registerAccount(), 로그인은 loginAccount()를 호출합니다.
  4. 이 함수들은 game-api.js를 통해 각각 register_game_account, login_game_account RPC를 호출합니다.
  5. 서버 응답에 profile이 있으면 브라우저에 필요한 프로필 정보를 저장합니다.
  6. render()가 로그인 화면을 숨기고 홈 화면을 표시합니다. 
registerAccount(nickname, password)
  → RPC: register_game_account

loginAccount(nickname, password)
  → RPC: login_game_account

성공한 응답
  → saveSession(profile)
  → render()
  → 로그인 후 화면 표시

현재 프런트엔드 코드에서 비밀번호 형식은 영어 대소문자와 숫자로 이루어진 4~8글자로 제한됩니다. 이는 입력 형식 검사이며, 그 자체가 비밀번호 보안이나 서버 인증을 보장하는 것은 아닙니다.

5. 브라우저 세션은 어떻게 동작하나요?

game-api.js의 getSession(), saveSession(), clearSession()은 브라우저의 localStorage에 있는 arcade-profile 항목을 읽고 쓰고 삭제합니다.

  • getSession(): 저장된 JSON 프로필을 읽습니다.
  • saveSession(profile): 프로필을 JSON 문자열로 저장합니다.
  • clearSession(): 해당 저장 항목을 삭제합니다.

홈 화면은 authVersion이 2인지 확인하고, 다른 버전이면 기존 브라우저 세션을 지웁니다. 이 버전 값은 세션 데이터 형식을 구분하기 위한 것이며, 비밀 인증 토큰이나 서버가 검증한 신원 증명은 아닙니다. 

localStorage["arcade-profile"]
  ├─ authVersion
  ├─ id
  ├─ nickname
  ├─ coins
  ├─ is_developer
  └─ is_teacher

위 항목은 브라우저에 저장된 값입니다. 사용자가 브라우저 저장 내용을 수정할 수 있으므로, 중요한 작업의 권한을 이 값만으로 판단하면 안 됩니다.

6. Supabase RPC 통신 메커니즘

game-api.js는 Supabase URL 뒤에 /rest/v1/rpc/를 붙여 RPC 경로를 구성합니다. 각 호출은 POST 방식으로 JSON 본문을 전송합니다. 

브라우저
  → fetch(Supabase RPC URL)
  → POST + JSON body
  → Supabase 함수 실행
  → JSON 응답
  → 화면에 결과 반영

공통 함수는 네트워크 오류를 처리하고, HTTP 응답이 실패하면 서버가 반환한 메시지나 세부 정보를 이용해 오류를 표시합니다. 응답에 ok: false가 들어 있는 경우도 실패로 처리합니다.

현재 API 래퍼에서 사용하는 공개용 키는 브라우저에 노출될 수 있는 키입니다. 따라서 데이터 접근 권한과 중요한 작업의 검증은 데이터베이스 정책 및 서버 함수에서 올바르게 제한해야 합니다.

7. 개발자 탭과 개발자 센터의 권한 확인

홈 화면은 저장된 프로필의 is_developer 값이 참일 때 개발자 탭을 표시합니다. 탭을 누르면 프로필을 다시 확인한 뒤 developer/index.html로 이동합니다.

개발자 센터의 JavaScript는 프로필이 존재하고, authVersion === 2이며, is_developer === true인지 검사합니다. 조건이 맞지 않으면 권한 없음 화면을 보여 줍니다.

이 확인은 사용자가 실수로 접근하는 것을 막는 UI 제어에는 도움이 되지만, 브라우저에서 실행되는 검사이므로 실제 보안 경계가 될 수 없습니다. 사용자는 주소를 직접 입력하거나 브라우저 저장값을 바꿀 수 있습니다.

따라서 개발자 권한 변경, 계정 삭제, 코인 변경 등 민감한 작업은 서버 함수에서도 요청한 사용자의 권한을 확인해야 합니다.

8. 현재 API 래퍼에 정의된 주요 기능

  • register_game_account: 계정 생성 요청
  • login_game_account: 로그인 요청
  • get_game_settings: 게임 설정 조회
  • teacher_get_accounts: 교사 계정 목록 조회 요청
  • teacher_grant_coins: 코인 지급 요청
  • teacher_update_settings: 게임 설정 변경 요청
  • teacher_set_shortcut: 바로가기 설정 요청
  • teacher_set_account_role: 계정 역할 변경 요청
  • developer_set_account: 개발자 계정 설정 요청
  • teacher_flag_nickname, teacher_create_delete_challenge, teacher_delete_account: 닉네임 확인 및 계정 삭제 관련 요청

이 목록은 프런트엔드 API 래퍼에 정의된 요청 이름을 설명합니다. 서버 함수 내부에서 수행하는 정확한 SQL, 추가 검증 절차, 데이터베이스 정책은 해당 Supabase 함수와 SQL 정의를 확인해야 합니다.

9. 게임 설정은 어떻게 반영되나요?

홈 화면의 render()는 로그인된 프로필이 있을 때 getSettings()를 호출합니다. 이 함수는 get_game_settings RPC를 요청합니다.

응답의 omok_enabled와 rummikub_enabled 값에 따라 해당 게임 링크에 disabled-game CSS 클래스를 적용하거나 제거합니다.

즉, 홈 화면에서 링크를 비활성화하는 것과 서버에서 게임 데이터에 대한 접근을 차단하는 것은 서로 다른 일입니다. 실제 접근 제한이 필요한 기능은 서버에서도 확인해야 합니다.

10. 새 기능을 추가할 때의 기본 순서

  1. 화면이 필요하면 해당 HTML 페이지에 요소와 버튼을 추가합니다.
  2. CSS를 사용해 화면의 배치와 스타일을 정의합니다.
  3. 페이지 JavaScript에서 버튼 이벤트와 입력 처리를 작성합니다.
  4. 서버 데이터가 필요하면 game-api.js에 RPC 호출 함수를 추가하고, Supabase에 대응하는 서버 함수가 있는지 확인합니다.
  5. 서버 함수에서 사용자 권한, 입력값, 대상 데이터와 변경 가능 범위를 검증합니다.
  6. 정상 요청, 권한 없는 요청, 잘못된 입력, 네트워크 오류를 각각 테스트합니다.
  7. 개발자 센터에서 접근할 수 있도록 필요한 링크를 추가합니다.

11. 보안상 꼭 알아야 할 점

  • 브라우저의 localStorage 값은 사용자가 수정할 수 있습니다.
  • 숨겨진 버튼이나 페이지의 권한 확인은 서버 보안을 대체하지 않습니다.
  • 공개용 Supabase 키는 비밀 키가 아닙니다. 서버 비밀 키나 service_role 키를 프런트엔드 코드에 넣으면 안 됩니다.
  • 민감한 RPC 함수는 서버에서 권한과 입력값을 검증해야 합니다.
  • 데이터베이스의 RLS 정책과 함수 실행 권한도 함께 점검해야 합니다.
  • 비밀번호의 실제 저장 방식과 서버 측 검증 방법은 SQL 함수 정의를 확인하기 전까지 단정할 수 없습니다.

12. 문제가 생겼을 때 점검 순서

  1. 브라우저 개발자 도구의 Console에 JavaScript 오류가 있는지 확인합니다.
  2. Network 탭에서 Supabase RPC 요청이 전송되는지 확인합니다.
  3. 응답 상태 코드와 서버 오류 메시지를 확인합니다.
  4. 파일 경로와 대소문자, HTML의 요소 ID가 일치하는지 확인합니다.
  5. 서버 함수 이름과 요청 JSON 필드명이 일치하는지 확인합니다.
  6. 권한 문제라면 브라우저 화면뿐 아니라 서버 함수와 RLS 정책을 확인합니다.
